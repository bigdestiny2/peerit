Split Transport —
Client-Side Route Separation

How a client's IP address and browser origin get separated from its storage requests, so the relay cannot bind "who asked" to "what was asked for." Two profiles: OHTTP for browsers, Protomux split for native. Both target G2-W + G4-T under non-collusion.

Prior art in your brain

This spec composes with three existing research documents in the p2p brain: NYM-HIVERELAY-METADATA-PRIVACY-SPEC (control-plane mixing), TOR-V3-RELAY-ANONYMITY-SPEC (relay-side location hiding), and RELAY-ANONYMITY-DECISION-MATRIX (the five-candidate study). This document adds the missing piece: client-side route separation — hiding the client's IP/Origin from the storage relay.

Guarantee ceiling — honest

G2-W (wire opacity) + G4-T (route separation) under A/B non-collusion. NOT G4-I. NOT traffic-analysis resistance. NOT global-observer resistance.

02Dev-profile design review

Before writing the wire protocol, the design was reviewed against three engineering lenses from the p2p brain. Their pressure shaped the spec; their approvals are recorded here.

FV Filippo Valsorda — security-first minimalism

Applied pressure: zero-config key discovery (not manual config); small explicit keys (one Ed25519-signed structure); strong defaults (fixed padding buckets, not configurable); UNIX composability (ingress and gateway are separate processes, no shared state).

Approval: "The OHTTP path is the right shape — RFC 9458 is a reviewed standard, not invented crypto, and the gateway key config is minimal and self-certifying. The opaque-origin iframe construction is the one piece I'd want to see wire-captured across all three browser engines before believing it. Don't ship 'application-blind ingress' until that evidence exists; 'storage-wire app opacity' is the honest label until then."

YA Yawning Angel — protocol-heavy correctness

Applied pressure: explicit invariants and fail-fast (every frame has exact-length checks, reserved-bit rejection, domain-separated signatures); extensive vector-based testing (byte-exact test vectors for every frame type); small focused packages (OHTTP codec, ingress forwarder, gateway decapsulator are separate modules); clear separation between protocol state, primitives, and test scaffolding.

Approval: "The frame format is sound — domain-separated, fixed-width integers, no host-language serialization on the wire. The Protomux split is the right first build because it reuses existing Noise primitives. Two things I'd insist on: (1) the FORWARD family's flow control (WINDOW/DATA offset) MUST be exactly the spec's, not a re-derivation — flow control bugs are how you get memory exhaustion; (2) the OHTTP key rotation overlap window MUST be at least 2 epochs, and clients MUST reject any config whose validity exceeds 30 days. Both are in the spec; keep them there."

DMC David Mark Clements — hot-path performance

Applied pressure: optimize the hot path (HPKE seal/open is sub-millisecond; the real cost is the extra network hop); treat benchmarks as product surface (p50/p95 latency gates); preserve compatibility (both profiles carry the same canonical blind-service messages); keep public APIs explicit and small (one client function: blindRequest()).

Approval: "The hot path is clean — one HPKE seal + one HTTP round-trip for browsers, one Noise frame + one forward hop for native. The extra latency is the real cost, not the crypto. Two things: (1) the padding buckets MUST be benchmarked — don't pad everything to 32 KiB just because it's simpler; measure the actual request size distribution and pick buckets that cover 95th percentile without wasting bandwidth. (2) The Protomux forward path reuses forward-relay.js's caps — good, don't add a second cap system."

04Profile 1: OHTTP for browsers

Standards used

  • RFC 9458 — Oblivious HTTP. Request/response encapsulation using HPKE.
  • RFC 9180 — HPKE. One-shot seal/open.
  • RFC 9292 — Binary HTTP. bHTTP framing for the inner request.
  • No new cryptographic constructions. No invented HPKE suites.

Gateway key configuration

The gateway publishes a signed key config. Clients fetch it via DESCRIBE on the ingress or through the signed capability document.

0 1 version = 1 1 32 gatewayRelayKey // Ed25519 pubkey of gateway operator 33 1 configId // rotation identifier 34 2 kemId // default: 0x0010 = DHKEM(X25519) 36 2 kdfId // default: 0x0001 = HKDF-SHA256 38 2 aeadId // default: 0x0001 = AES-128-GCM 40 [1..256] encodedPublicKey // KEM public key .. 4 notBeforeEpoch // seconds, inclusive .. 4 notAfterEpoch // seconds, exclusive .. 0/32 previousConfigHash // optional: BLAKE2b-256 for chained rotation .. 64 signature // Ed25519 by gatewayRelayKey

Signature domain: ASCII("hiverelay.blind.ohttp-key-config.v1\0") + all preceding bytes.

Key rotation rules (Yawning's insistence)

  • Configs MUST overlap for at least 2 epochs during rotation.
  • Clients reject: rollback below a witnessed config, unknown suites, validity > 30 days, or reuse of configId with different key bytes.

Request encapsulation (per operation)

1 Build inner binary HTTP request (RFC 9292): POST /api/blind/v1/cell with the canonical BlindDispatchFrameV1 body. No Origin, Referer, Cookie, or Client-Hint headers.
2 HPKE seal (RFC 9180) using gateway's public key. Fresh context per request. info = "ohttp-req" || configId. Output: enc || ciphertext.
3 Wrap in OHTTP envelope (RFC 9458 §3): configId || enc || ciphertext.
4 Pad to the next negotiated size bucket (see below).
5 POST to the shared generic route: POST /ohttp-req. Same URL for all apps.

Oblivious ingress service

The ingress is a new HiveRelay role — deliberately minimal:

Receive POST /ohttp-req ├── Verify Content-Type = application/ohttp-msg ├── Read configId from byte 0 ├── Look up gateway route for this configId ├── Strip ALL browser headers: │ Origin, Referer, Cookie, Set-Cookie, Client-Hint-*, │ Sec-Fetch-*, Sec-CH-*, User-Agent, Accept-Language, │ Forwarded, X-Forwarded-For, X-Real-IP ├── Forward ONLY: │ opaque OHTTP message body │ + generic gateway route │ + ingress correlation ID (random 16 bytes, response-matching only) └── Return gateway's opaque response to browser

Critical: the ingress does NOT decrypt the OHTTP message. It sees only "a browser at IP X sent an opaque blob to gateway Y."

Padding classes (DMC's benchmark gate)

ClassRequest bytesResponse bytesUse case
01 KiB1 KiBDESCRIBE, small CELL.GET
14 KiB4 KiBCELL.PUT (typical post), INBOX.READ
216 KiB16 KiBCELL.PUT (long body), BATCH_GET
364 KiB64 KiBMaximum single request

Client picks the smallest bucket that fits. No per-request negotiation — bucket determined by size alone.

The opaque-origin iframe construction

<iframe sandbox="allow-scripts"     <!-- NO allow-same-origin → opaque origin -->
        src="about:blank"
        style="display:none"
        id="ohttp-worker">
</iframe>
  • Communication via MessageChannel — bounded binary jobs only.
  • credentials: "omit", referrerPolicy: "no-referrer" on all fetches.
  • Achieves: Origin: null instead of Origin: https://peerit.site.
  • Does NOT achieve (until proven): some browsers may leak app origin via SNI, TLS session resumption, cache timing, service worker, or error messages. Conformance gate (§7) requires wire-capture proof across Chromium, Firefox, Safari/iOS.

Honest label until wire-capture passes

"Storage-wire app opacity" — NOT "application-blind ingress." The difference matters: the former means "we stripped the obvious headers"; the latter means "we proved no channel leaks the app." Upgrade the label only after the P3-W wire-capture gate passes.

05Profile 2: Protomux split for native

What's reused

The existing forward-relay.js already provides a demand-dialled byte bridge with onion composition and caps. This profile upgrades the framing — not the topology.

Existing (shipped)What changes
OPEN(target) / DATA(bytes) / CLOSEUpgraded to BlindForwardOpenV1 / DataV1 / WindowV1 / CloseV1 with circuit nonces, commitments, flow control, signed open-results
64 MB/forward, 5/peer, 30 dials/min, 64 KB/frameUnchanged — reuse, don't re-derive (DMC's pressure)
connectViaForward(relay2, relay1) for 2-hop onionUnchanged topology; new framing rides on top

BlindForwardOpenV1 frame

0 1 version = 1 1 32 targetPubkey // exit/storage relay's Ed25519 key 33 16 routeId // random, identifies this circuit 49 32 nextDescriptorHash // BLAKE2b-256 of next hop's signed descriptor 81 32 circuitNonce // random, binds all frames on this circuit 113 4 requestedInitialWindow // 64 KiB..1 MiB 117 4 requestedIdleMillis // 1000..120000 121 4 requestedLifetimeMillis // 1000..3600000 125 32 hopAdmission // anonymous quota token or PoW 157 32 requestCommitment // BLAKE2b-256 of all preceding fields 189 64 signature // Ed25519 by the entry relay's key

Domain: ASCII("hiverelay.blind.forward-open.v1\0")

BlindForwardDataV1 / WindowV1 / CloseV1

// DATA — opaque payload, offset-based flow control 0 1 version = 1 1 32 circuitNonce 33 8 offset // strictly increasing, next expected byte 41 n bytes // 1..maxDataBytes, Noise-encrypted // WINDOW — credit-based backpressure 0 1 version = 1 1 32 circuitNonce 33 8 consumedThrough // bytes consumed by next hop 41 4 creditIncrement // 1..1 MiB; total credit stays capped // CLOSE — FIN (send side) or ABORT (both sides) 0 1 version = 1 1 32 circuitNonce 33 1 closeKind // 1=FIN, 2=ABORT 34 8 finalSendOffset 42 1 reasonCode // generic enum, no app text

Yawning's flow-control insistence

"Flow control bugs are how you get memory exhaustion." The WINDOW/DATA offset mechanism MUST be exactly the master spec's §7.3.2 — not a re-derivation. At zero credit the adapter stops reading upstream. No unbounded queues. Ever.

End-to-end Noise session

On top of the forward circuit, the client and storage relay run a separate Noise XX handshake. The Noise session carries the canonical blind-service messages (CELL/INBOX/CORE/DESCRIBE). The forward relays see only Noise-encrypted bytes — exactly like Tor relays see only cells.

Fallback policy

strict mode:
  if no split path available → FAIL CLOSED
  never silently use direct

balanced mode:
  if no split path available → explicit user/policy permission
  claim downgrades visibly in the UI
  log the downgrade in coverage evidence

06Transport descriptors

Both profiles require signed, expiring transport descriptors advertised via DESCRIBE:

0 1 version = 1 1 32 relayIdentityKey // stable Ed25519 operator key 33 1 role // 1=ingress 2=gateway 3=entry 4=exit 5=storage 6=onion 34 2 protocolVersion // hiverelay-blind major.minor 36 [..] endpoint // URL (OHTTP) or pubkey (Protomux) .. 0/32 ohttpConfigHash // if role=ingress: hash of current key config .. 1 paddingClasses // bitmap of supported size classes .. 4 notBeforeEpoch .. 4 notAfterEpoch .. 64 signature // Ed25519 by relayIdentityKey

Clients select transports based on: signed descriptor validity, privacy policy (strict/balanced), operator diversity (entry ≠ exit ≠ storage?), and health (endpoint reachable?).

09Honest claim ladder

"Your IP is hidden from the storage relay"
True
"The ingress cannot read your request"
True
"The storage relay cannot tell which app from the wire"
Partial
"The storage relay cannot tell which post you read"
False
"Your traffic is anonymous"
False
"It resists a global observer"
False

Forbidden claims

"anonymous," "untraceable," "the relay can't see you." All imply stronger properties than split transport delivers.

Permitted claims

"Source-IP-separated under non-collusion." "Request content hidden from the ingress." "Storage-wire app opacity (pending wire proof)."

What does NOT change

  • The canonical blind-service messages (DESCRIBE/CELL/INBOX/CORE/FORWARD) are unchanged.
  • Application logic (peerit's posts, votes, moderation) is completely unaware of which transport is in use.
  • The blind substrate's storage guarantees (G0/G1/G2-S/G3) are independent of transport. Split transport adds G2-W/G4-T on top.
  • Adding FORWARD frames to the wire requires an abiHash bump — all conforming clients and relays update together.
