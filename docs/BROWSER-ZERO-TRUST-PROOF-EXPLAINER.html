The browser is a zero-trust client now

A completely stock Chrome — no extension, no flags, no install — can now be a full, cryptographically self-verifying client of the blind P2P substrate, under a strict production CSP. It was never true before. It is true now, three browser versions deep, with receipts.

Historical proof snapshot: this page records the seq-20 browser proof. Repository main now carries accepted release sequence 26 with the same GET-only trust boundary plus subsequent recovery and first-visit fixes.

01What was achieved

A fresh browser, given nothing but a signed bootstrap artifact and two relay URLs, can now do all of the following on its own:

  • Verify the relays before trusting them. It walks each relay's descriptor chain back to a pinned genesis and checks every Ed25519 signature locally. No trust assumption, no "because the site says so."
  • Cold-recover the entire seeded forum. It enumerates all 11 launch communities and assembles the feeds — 40 verified CELL.GETs and 0 PUTs — pulling 39 live records and checking every one byte-for-byte against what was published, boxed blob payloads included.
  • Do it under a strict production CSP. script-src 'self' — no unsafe-eval, no wasm-unsafe-eval — with zero CSP violations and zero page errors, identically across Chromium 145, 149, and 151.

The property this delivers: the browser trusts math, not the relay. Every post, comment, and community on the page is verified against its author's signature on the user's own machine. The relay can withhold data. It can never forge it.

02What was blocking it — and why nobody saw it

The browser bundle's crypto libraries eagerly compiled WebAssembly at import. Under a strict CSP, that is a hard CompileError — the entire module graph dies before one line of application code executes. The app was completely unrunnable in a real browser.

The chain of the defect

bundle import
  └─ sodium-universal
     └─ sodium-javascript@0.8
        ├─ sha512-universal → sha512-wasm   ← synchronous new WebAssembly.Module() at import — the import-killer
        └─ blake2b          → blake2b-wasm  ← async compile left as an unhandled rejection

The uncomfortable part is why it was invisible:

  • Every prior proof ran in Node. Node has no CSP. Write/readback drills, cold-recovery proofs, canary drills — all green, all in an environment where the defect cannot exist.
  • The accepted release line listed the browser gate as a retained hold. The seq-19 acceptance named the live-two-relay Chromium gate among items explicitly not executed. The browser path had literally never been run.
  • The static gates would have passed anyway. They verify decision documents and continuity — not browser behavior. The bundle would have shipped browser-broken with every checkbox green.

It only surfaced because the launch chain had a rule: a real Chromium gate passes, or nothing ships. The gate ran, on three Chrome versions, and caught what review and CI had both missed — a latent ship-blocker in an accepted artifact.

03The fix — and why it's the right fix, not the cheat

The easy way out was to relax the CSP — add wasm-unsafe-eval and let the page weaken its own security posture to make the app run. Both owner decisions explicitly forbid that. So the fix went the other way: the WASM packages were aliased out of the browser build entirely.

Artifact-side, zero-WASM

Checked-in stand-ins answer "unavailable" through the exact ready() / SUPPORTED surface the libraries expect, so their built-in pure-JS fallbacks execute instead. Result: zero WASM bytes in the bundle, zero violation attempts, CSP untouched.

Note the intermediate failure: a first pass that merely wrapped the compiles in try/catch still produced wasm-eval securitypolicyviolation reports — an attempted compile is a violation even when caught. The packages had to go, not be wrapped.

Why it's legitimate and not a hack

The protocol is byte-identical either way. The same request construction was run through three engines and produced identical bytes:

04Why it's significant

The dual-ship claim is finally honest

Peerit's pitch has always been "same signed data, two ways to run — native P2P or a normal browser." Until this week, the normal-browser half of the blind-substrate path was aspirational: it had never been executed under a real CSP. Now it has receipts.

Zero-install zero-trust works in practice

A user who installs nothing can read a P2P forum whose integrity depends on no server. That is the entire point of the architecture — demonstrated end-to-end for the first time, in the environment users actually have.

CSP-safe P2P deploys anywhere static

No WASM, no eval, no plugins: the entire client is static files that can sit on any host — Render, Cloudflare Pages, IPFS — behind a hardened CSP. "P2P apps that deploy like plain web pages" is a genuine distribution unlock, and it's what makes "try it in a tab, graduate to native" real instead of a slogan.

The catch matters as much as the fix

A latent ship-blocker inside an accepted release was caught because the chain refused to trust static gates. That discipline — evidence over checkboxes — is the same discipline that caught the atomic-ingress deployability gap and the probe-purge ambiguity earlier in the same launch. It is the reason the launch is honest.

05The honest boundary

Significance without inflation:

  • What is proven is the read/recovery path in stock browsers. INBOX/CORE client composition remains limited.
  • The GA product gate stays closed — 22 blockers disclosed-open in the release evidence, not hidden.
  • The relays are two owner-operated failure domains. This is a bounded public-test canary, not independent operation, and it is labelled that way everywhere.
  • The seq-19 accepted bundle carries the same latent defect; it is recorded in the disclosure ledger for reassessment after this fix line.

The specific new truth is narrow and exact: a stock browser can be a verified client of the blind substrate under real CSP. Everything broader — full consumer GA, independent operators, complete INBOX/CORE — is future work, and it says so on the label.
