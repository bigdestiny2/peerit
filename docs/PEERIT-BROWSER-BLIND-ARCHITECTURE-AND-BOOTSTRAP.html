Blind client in a normal browser — not Bare-in-Chrome, not a trusted API

How peerit.site reaches the same signed social world as PearBrowser without pretending the browser joined Hyperswarm: pure-JS vendored clients under hard CSP, a signed seed bootstrap for cold start, dual-relay Cell-GET recovery, and an honest split between P2P integrity and relay-assisted availability.

1. Claim boundary (read this first)

Fair to claim

  • P2P data model in the browser (signed records, client merge)
  • P2P integrity (relay cannot forge)
  • Blind custody (relays hold opaque cells)
  • Cold start from a signed seed bootstrap + GET-only recovery
  • Works under production CSP script-src 'self' with pure-JS clients

Overclaim / false

  • “We have full P2P in the browser”
  • “Bare / Hyperswarm worker runs in Chrome”
  • “No middleman for browser users”
  • “Browser is a DHT node”
  • “Independent multi-operator network” (today: two owner-operated relays)
A normal browser is never a standalone DHT node. There is always a reachable relay (or bridge) in the path. What Peerit ships is the best honest substitute: a blind client of a P2P network. — Peerit honest ceiling (Browser Pear Apps)

5. How this architecture was achieved

Not a single flip. It is a replacement production path (blind substrate) layered under the same Peerit app protocol, then hardened through launch sequences 13→20.

Design moves that made it possible

  1. Separate app meaning from transport. Model, ranking, mod, identity stay Peerit-owned. Network I/O becomes generic Blind DESCRIBE / CELL surfaces. Relays stay app-agnostic.
  2. Accept the first-hop constraint. A cold browser cannot introduce itself to another browser. Something reachable must exist. Design for an untrusted reachable helper, not for pure browser-to-browser fantasy.
  3. Vendor the blind clients into the web release. Control + Cell-GET artifacts are pinned, evidenced, and verified at boot — not “npm install something at runtime.”
  4. Make recovery GET-only and sequence-gated. Limited Cell-GET authority exposes only at the live sequence (20). Any other sequence fails closed before relay I/O.
  5. Name the launch seed cryptographically. PeeritSeedBootstrapV1 lists records + dual read capabilities. Empty reader + artifact → 34/34 byte-exact recovery proven.
  6. Survive production CSP. Rebuild clients pure-JS (no eager wasm) so script-src 'self' does not brick Chromium with CompileError / CSP violations.

6. Pure-JS clients under hard CSP

Production peerit.site ships a strict policy: script-src 'self', no unsafe-eval, no wasm-unsafe-eval. That is intentional (smaller attack surface, harder supply-chain tricks) — and it broke the first generation of browser blind clients.

Before (failed on live CSP)

  • Vendored clients eagerly compiled WebAssembly at import
  • sha512-wasm sync / blake2b-wasm async probes
  • Even a caught CompileError still fires securitypolicyviolation
  • seq-20 Chromium gate: FAIL under unchanged production CSP

After (CSP-safe pure-JS)

  • Wasm packages aliased out entirely
  • Pure-JS fallbacks; byte-identical crypto output
  • Zero wasm bytes, zero compile attempts
  • Control ~224 KB · Cell-GET ~174 KB
  • Chromium 145/149/151 production gate: PASS

What this buys: a real browser can run the full verify/reconstruct path without relaxing CSP to “whatever crypto needs.” That is a shipping barrier, not a research demo. It is not the DHT barrier — pure-JS does not create UDP sockets or swarm membership.

Boot-time verification (not “trust the CDN”)

Runtime authority loads pinned paths under /vendor/hiverelay-blind-client-v1/ and /vendor/hiverelay-blind-cell-get-v1/, checks manifests, authority.json, and chromium/cross-host evidence before any relay call. Caps bound download size and assembly time so a huge malicious asset cannot hang the tab forever.

8. DMC lens — first hop, constraints in tension, when AI fails

David Mark Clements’s feedback shaped both the architecture and the process around it. Two different lessons — one technical, one operational.

8.1 Technical: the first hop is not optional

A browser can’t make the first hop to another browser on its own — something reachable has to introduce them. Designs that try to “remove the pipe entirely” can be coherent, detailed, and still useless if that assumption is a fantasy. — Operator summary of DMC pushback (Peer-to-Pears creator story)

That killed a whole class of “pure browser-to-browser bootstrap” rabbitholes. Peerit’s answer is not “no pipe.” It is:

  • pipe is real and allowed,
  • pipe is blind (no app truth),
  • pipe is untrusted for integrity,
  • pipe is dual (dal + syd) for bounded availability,
  • cold discovery is a signed artifact, not “ask the pipe what exists.”

8.2 Process: deep novel work is where LLMs thrash

From a recent DMC conversation (paraphrased / quoted for the working notes):

  • Once you’re past pattern-matching depth, models start “winging it on crazy tangents.” You burn days, then get a polished apology and a blank “what would you like to do now?”
  • Context growth makes every wrong swing expensive — a few off-tracks can eat a third of budget just to re-rail.
  • At the frontier of a pet project, the hard part is holding constraints in tension. Models either inject unexplained “crucial” bits or drop a minor-sounding note that invalidates the whole design.
  • Analogy: like approaching the speed of light — the closer you get to the real edge of the problem, the more the medium works against you. Diminishing returns are real.
  • Independent code review still leaves implementation work. Eventually you need one or two strong devs onboarded to P2P to get it across the line.
  • Upside of AI: experiment for PMF (Peerit included) before paying full man-hours — then put real resources into users when the shape is interesting enough.

Why this belongs in an architecture doc: the blind-client design, the withdrawn /api/boot, the CSP pure-JS fight, and the signed seed bootstrap are all artifacts of holding those tensions deliberately — and of checking assumptions with humans who have built this class of system before. The architecture is as much “what we refused to claim” as “what we shipped.”

9. Tiny-file / data-URL bootstrap idea (related, not shipped)

A separate research track (Pear-dev chat → DATA-URL-BOOTSTRAP-SCOPE.md) asked: can we shrink first contact to a tiny pasteable stub so the hosted origin is not the permanent code authority?

Diagram G · tiny stub dream vs browser facts

The tiny-file idea and the signed seed bootstrap share DNA (small signed root → fetch → verify) but solve different layers: code delivery vs data cold-start. Seed bootstrap shipped for content; data-URL bootstrap remains scoped research, not the production path.

Do not merge these stories in marketing. “Tiny pasteable Peerit” is not what peerit.site is today. Today is: normal HTTPS origin + hard CSP + pure-JS + signed seed bootstrap + blind cells.

10. Language you can use

Public one-liner:
Chrome still can’t be a Hyperswarm peer — that barrier is real. Peerit.site is a blind client: keys and verification in the browser, dual geo cells for availability, and a signed seed bootstrap so a cold tab can recover the launch world with GET-only Cell reads under production CSP.

For builders

Axes 1–3 achieved in a normal browser; axis 4 only in PearBrowser. First hop requires a reachable helper; we made the helper blind and the cold-start artifact application-owned and reverse-bound by release authority.

For users

Open peerit.site like a normal site. Your browser checks every post. Relays store sealed cells, not a company database of your feed. For the strongest path, use PearBrowser.
